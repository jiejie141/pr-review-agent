# 实验记录

按时间顺序记录每一次「发现问题 → 定位根因 → 改动 → 复测」的完整过程。
数字全部来自 `eval/run_eval.py` 的实际输出，没有估算。

评测四项指标的口径：

| 指标 | 回答的问题 |
| --- | --- |
| 规则召回 | 标注好的缺陷，模式库能抓到多少 |
| 负数误报 | 干净的改动上会不会无中生有 |
| 锚定有效率 | 模型给的行号有多少真实存在（幻觉率） |
| 语义命中率 | 正则抓不到的语义缺陷，模型能不能理解 |

## 实验 1：规则库首跑，78.6% 召回

**现象**：首次跑 `eval/run_eval.py --mode rules`，18 个用例。

```
规则召回    : 22/28 = 78.6%
漏报的规则  : CONV302, CONV303, CONV307, CONV308, PERF205, PERF206
负数误报    : 8 条 / 3 个干净用例（1 个用例被误报）
```

**归因**：漏报集中在**带 `^` / `$` 锚点的单行规则**上，这个聚集本身就是线索。

**根因**（重要的架构 bug）：`RuleEngine._target_text()` 写成了一次性判断 ——

```python
needs = [p for p in self.patterns if p.needs_context]
if not needs or ln.new_no is None:
    return ln.text
return f.context_window(...) or ln.text
```

只要模式库里**存在任意一条** `needs_context=True` 的模式（PERF201 等），
`needs` 就非空，于是**所有**模式（包括单行规则）都被拿去匹配多行窗口。
而非 MULTILINE 的 `^` 只匹配字符串开头、`$` 只匹配字符串结尾，
所以 `^\s*except\s*:\s*$` 这类规则**永远不可能命中**。

一个模式库里的局部特性污染了全体模式的行为 —— 这是典型的「作用域没收敛」。

**改动**：把窗口判断从「全局一次」改成「逐模式计算」，并在循环内加注释说明为什么不能共用。

**复测**：

```
规则召回    : 26/28 = 92.9%   （CONV302/303/307/308 全部恢复）
负数误报    : 2 条 / 3 个干净用例
```

## 实验 2：定位两处误报与两处漏报

**误报**：`n02_clean_http` 上 `SEC108`（SSRF）报了 2 条。该用例的代码是：

```python
def fetch(url, timeout=5):
    try:
        return requests.get(url, timeout=timeout).json()
```

**根因**：`SEC108` 只要看到「调用了发请求的函数」就报，完全不看 URL 来自哪里。
单行正则做不到数据流分析 —— 而 `requests.get(url)` 里的 `url` 完全可能是本地常量。

**取舍决定**：收紧为「变量名必须带外部来源信号」（`callback` / `user_` / `req.query` / `params[` …）。
这会**漏掉一部分真实 SSRF**，但误报的代价更高：一个在干净代码上乱报的工具，没人会用第二遍。

**漏报** `PERF205`（循环内建连接）：原正则要求 `.connect(` 紧跟标识符，
`sqlite3.connect(` 和 `db.Session(` 这类带模块前缀的写法全部漏掉。
改成 `[^\n]*` 吃掉前缀。

**漏报** `CONV307`（用 assert 做校验）：原正则 `assert\s+[\w.\[\]()"']+\s*,` 要求断言表达式里
**没有空格**，而 `assert amount > 0, "msg"` 中间有 `> 0`。
改成 `assert\s+[^,\n]+,\s*["']` —— 「assert + 附带错误消息」才是最典型的误用信号。

**复测**：召回 28/28，误报 0。

**但这次结果不可信** —— 模式库是照着这批用例调的，属于自己出题自己答。

## 实验 3：加留出集，并把注释纳入规则的作用域

**动机**：自出题自答拿 100% 没有信息量。新增 4 个**未参与调参**的用例：

- `h01_format_sql`：`.format()` 拼 SQL，且**注释里提到**历史上用过 `pickle.loads`
- `h02_provider_key`：硬编码第三方 API Key
- `h03_comment_traps`：全是注释陷阱（见下）
- `h04_clean_subprocess`：列表参数调用外部命令 + 带超时的请求

**h03 的构思**：注释里写危险写法，代码本身干净。

```python
def safe_copy(src, dst):
    # 不要用 os.system(cmd) 去拷贝，会有命令注入
    # 也不要写 requests.get(url, verify=False)
    # 更不要图省事用 eval(expr) 解析配置
    with open(src, "rb") as f_in, open(dst, "wb") as f_out:
        f_out.write(f_in.read())
```

**首测结果**：h03 报了 3 条 —— `SEC102`、`SEC106`、`SEC104` 全部在注释上误命中。

**根因**：规则引擎对整行文本做匹配，不区分代码区和注释区。

**改动**：
1. 新增 `comment_start(line, suffix)` —— 识别 `#` / `//` / `--`，并跳过字符串字面量内部的标记
   （否则 `print("a # b")` 会被误判成后半行是注释）；
2. `Pattern` 增加 `ignore_comments: bool = True` 字段；
3. `CONV304`（检查遗留 TODO）**显式关闭**该行为 —— 它检查的就是注释内容。

**复测**：

```
规则召回    : 30/30 = 100%
    · 调参集 : 28/28
    · 留出集 :  2/2      ← 这才是可对外说的数字
负数误报    : 0 条 / 5 个干净用例
```

**必须写下来的局限**：留出集只有 2 个正例，样本量不足以支撑任何统计结论。
它验证的是方法可用，不是「准确率 100%」。

## 实验 4：离线替身本身在污染基线

**现象**：切到 `--mode mock`（规则 + 离线替身）后，负数误报从 0 涨到 4 条，分布在 3 个干净用例上。

**根因**（替身自身的三个缺陷）：

1. 没有注释守卫 —— `h03` 的注释陷阱再次被替身命中；
2. 「缺少事务边界」只看**单个**写操作 —— 一个 `execute` 就报事务问题，纯噪声；
3. 参数名校验把 `path` 也算作敏感参数 —— 但 `def f(path)` 太常见了。

**改动**：给替身加上同样的注释守卫；事务判断要求分片内**至少两个**写操作；从关键词里去掉 `path`。

**复测**：

```
负数误报    : 0 条 / 5 个干净用例
锚定有效率  : 11/11 = 100%
语义缺陷命中率 : 1/1 = 100%
```

**口径提醒**：替身的锚定有效率**必然是 100%** —— 它只输出输入里真实存在的行号。
这个指标在这里证明的是「链路正确」，**不是**模型幻觉率。要测幻觉率必须换真实模型。

## 实验 5：单元测试暴露的四处代码缺陷

写测试的过程中，测试把代码的问题逼出来了（而不是反过来改测试去迁就代码）：

**5.1 JSON 解析优先数组，导致外层对象被丢掉**

```python
# 原实现
for opener, closer in (("[", "]"), ("{", "}")):   # 固定优先数组
```
输入 `{"findings": [{"line": 3}]}` 时，内层的 `[` 先被截取成候选，
结果只拿到 `findings` 数组、丢掉外层对象。改成**按起始位置排序**，最早出现的容器优先。

**5.2 `PERF204` 把「已分页的查询」误判为全量加载**

`limit(50).all()` 照样命中「未分页全量加载」—— 这属于最伤可信度的误报类型。
用负向先行断言排除含有 `limit|offset|first|take|paginate` 的行。

**5.3 `SEC101` 漏掉最常见的 Python 注入写法**

`execute("... = '" + name + "'")` 这种「SQL 里嵌引号再接 `+`」的写法，
会被内层引号截断，前四条正则全部抓不到。补一条专门的规则。

**5.4 检索只索引正文，不索引标题**

规范文档里的「异常处理」「密钥与配置」这类**章节名**本身是最强的检索信号。
不索引标题导致「裸 except 吞异常」这类查询全部落空。把标题并入索引文本。

**5.5 单个巨大 hunk 无法分片**

新增文件在 diff 里就是一个巨大的 hunk，按 hunk 分片会把整个文件塞进同一个分片。
分片粒度改为**行**。同时修掉分片可能重复收录行号的问题。

**顺带记录一个测试自身的 bug**：`test_list_files_paginates` 用 `"page=1" in path` 判页码，
而 `per_page=100` 里**就包含 `page=1` 子串**，桩函数永远返回同一页 → 测试死循环 → MemoryError。
改用解析 query string 取 `page` 参数。

**复测**：314 项测试全通过，评测指标无回归。

## 实验 6：同一个缺陷被报 5 次

**现象**：跑 `python main.py --diff examples/demo.patch --mock`，输出里出现：

```
[MEDIUM] PERF201   app/orders.py:11
[MEDIUM] PERF201   app/orders.py:12
[MEDIUM] PERF201   app/orders.py:13
[MEDIUM] PERF201   app/orders.py:14
[MEDIUM] PERF201   app/orders.py:15
```

**代码只有一处循环**：

```python
def load_orders(user_ids):
    rows = []
    for uid in user_ids:
        rows.append(repo.query(Order).get(uid))
    return rows
```

**根因**：跨行模式对「当前遍历的每一行」都取一次上下文窗口，
而循环体内每一行的窗口**都包含那个 `for`**，于是同一个缺陷被反复命中。
这类噪声会让报告完全失去可读性。

**改动**：把跨行模式的锚点从「当前遍历行」改成**匹配起始行** ——
用 `target[:m.start()].count("\n")` 把匹配起点映射回扁平行列表的下标，
锚到那一行。这样循环体内所有重复命中会收敛到同一个 `(规则, 行号)`，
被去重集合自然滤掉。顺带给 `DiffFile` 加上 `flat_lines()` 与返回起始下标的 `context_slice()`。

**复测**：

```
[MEDIUM] PERF201   app/orders.py:14     ← 精确落在 for 那一行，只报一次
```

新增 `tests/test_rules_context.py` 共 8 项测试钉住这个行为，包括：
- 同一循环只报一次
- 两处独立循环分别报出
- 锚定行必须真实存在于新增行集合中
- 单行模式的锚点不受影响
